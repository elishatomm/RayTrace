## Demonstrations

All three use rules mode and new, empty data directories. Wall-clock times are single runs (n=1), so they are not a latency benchmark.

**A. A successful recovery** (`run_53966a08d4`, worker_backlog seed 101; 14 steps, 4,604 ms):

- Before recovery, the queue showed 98 captured orders whose processing never finished (INR 119,592.00).
- After the read-only provider refresh, plan hash `9db6c8c60bee4995…` named 103 orders. It was approved by `op_demo_operator`.
- Execution: fulfilments went from 45 to 148. Executing again and exporting the receipt twice left them at 148.
- The receipt `eb9d6f30f04d9ebc…` reports:
  - 103 newly completed orders;
  - INR 125,027.00 of restored processing value;
  - 0 new captures;
  - 0 duplicate fulfilments;
  - 11 orders left unresolved (INR 18,291.00).
- The committed rows of that action agree, and so do the API's bytes and the report.

**B. An approval that becomes stale:**

- **B1, expiry** (`run_ec0065d1b6`, seed 102; 10 steps, 520 ms). This is the demo walkthrough's stale-approval beat: approve, advance the replay clock 15 minutes, then execute.
  - Execute answered HTTP 409: `approval_expired: approval expired at 1793969280000, now 1793969340000`. The refusal's own receipt shows 0 restored.
  - Fulfilments stayed at 51. Executing again replays the refusal, and approving the same plan again is refused.
  - A new plan needs its own approval.
- **B2, a refund after approval** (`run_53966a08d4`). The simulated provider's refund of `order_SYNTHETIC_547a954d_0049` arrived through the webhook route after approval.
  - Execute answered HTTP 409: `target_ineligible: order_SYNTHETIC_547a954d_0049: refunded`; `evidence_changed: the targets' state changed since the plan was built`.
  - Fulfilments stayed at 45.
  - In the queue, the order is now `business_state_conflict`, with next step `manual_review`.

**C. An unresolved payment state** (`run_8581d2ff66`, late_authorization seed 101; 7 steps, 650 ms):

- Order `order_SYNTHETIC_920abafa_0181` was `capture_not_confirmed`: its payment was authorised but not captured, and its next step was `hold`.
- The read-only refresh of 76 payments moved it to `notification_not_accepted`, with next step `prepare_provider_replay`. It is still not fulfilled and still counted as unresolved.
- Unresolved orders went from 2 to 5, and fulfilments stayed at 305. The escalation asks for `fetch_provider_snapshot`.

## Stress and fuzz

Each attack ran against the real server (uvicorn) inside a container with no network, in rules mode. Each was run 3 times on images built from the tested code, then once more independently against the release's own images. The probes are kept outside the repository.

| Attack | What held, in every run |
|---|---|
| 16 simultaneous executes of one approved Flow A plan | One execution and 15 replays of the same action. Fulfilments by reprocessing equal the plan's 103 targets, with no order fulfilled twice. The receipt is `eb9d6f30…` |
| 32 simultaneous deliveries of one signed webhook, and several event IDs reporting one capture | One inbox row per event ID with new bytes; the same bytes under a new ID are a duplicate. After the worker runs, the order has exactly one fulfilment |
| 588 malformed webhook requests (bad, missing or duplicated signatures and event IDs, broken or deeply nested JSON, bodies around the size limit, long headers) | No 5xx. `/health` answered throughout. Orders, payments, fulfilments and actions were unchanged, and no inbox row was stored |
| Public mode: 30 simultaneous logins with the right token, 50 with wrong tokens, then the right one again | All 30 got 200. At most 20 sessions were live, and the evictions were logged. Wrong tokens got no session and the last login worked. Every answer carried HSTS, and there was no 5xx |

**Seen beyond these conditions, none of them letting money move wrongly:**

- **Two server processes on one data directory.** This is unsupported, because sessions, jobs and locks live in one process. One action and 103 fulfilments still held. But in 2 of 3 runs, 1–2 retries got HTTP 422 instead of a replay, and the receipt recorded a later execution time. Run one server per data directory.
- **Public mode, 64 or more idle connections.** New requests get uvicorn's own 503, without HSTS, until the 15 s request deadline closes them. This is documented in [DEPLOY.md](DEPLOY.md) and in [SECURITY_AUDIT.md](SECURITY_AUDIT.md) run 3: only the host's proxy can stop a connection flood.
- **A world whose deployed receiver is `receiver@2`** answers some malformed bodies with 500. That deploy is the simulated faulty receiver (incident family D3), documented in [RUNNING.md](RUNNING.md) section 8.
- **Smaller points:**
  - each replayed execute still advances the run's replay clock by a minute;
  - login refusals from the failed-login window carry no `Retry-After`;
  - the production image, run with a read-only root and no writable `/data`, stops with a traceback.

## Found during verification

- **G07: an approval did not cover each target's payment, amount and currency.**
  - **The gap:** the recheck compared a stored target with its event by order ID only, while the executor wrote from the stored payment, amount and currency. So a target altered in the database after approval executed, with a receipt showing no failed check.
  - **Fixed** in `578d394`: the recheck now compares each stored target's event ID, payment, amount and currency with its event, and a difference fails `target_ineligible`. Plan hashes, the receipt format and every successful receipt are unchanged.
  - **Reaching it needed write access to the database.** In this project's threat model, that access already allows writing a fulfilment directly ([README, Boundaries](../README.md#boundaries)).
  - **Two residuals:**
    - such a refusal's receipt lists the altered order as a no-op with "plan rejected", though its failed check names the order, the field and both values;
    - the plan's total value, which feeds only displays, is not bound.
- **Two existing tests check that an expected code is present, not that it is the only one:** the expired-approval test and the altered-plan test. The gate tests above check single codes.

## Known limitations

- [README, Boundaries](../README.md#boundaries) lists the product's limits, and [SECURITY_AUDIT.md](SECURITY_AUDIT.md) lists what security audit run 3 left open.
- **Not run for this release:**

  - any deployment (nothing is published).
- The "UI offers re-evaluation" part of fixture B is shown through the API (B1's new plan), and the walkthrough covers the page's own steps.

## Disabled optional capabilities

None is disabled. A hosted model and public mode are off unless configured. The local model is optional, though the default mode, `local`, asks it first. Without it, a diagnosis needs review and the page offers the rules, and every flow runs with `WORKBENCH_MODEL_MODE=rules`.
